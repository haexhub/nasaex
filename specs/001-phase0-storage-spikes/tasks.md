## Rules that apply to every task

1. **Criteria first, frozen before the first recorded run** (spec FR-001, SC-002; plan open item O2). A "run" that can produce a record is a record-mode run. Shakedown runs (`--mode shakedown`) never count and never write records; criteria edits made after shakedown and before the freeze are normal pre-freeze edits noted in the criteria file's `changelog`. After `spikectl freeze <spike>` the criteria PR must be merged before any record-mode run of that spike. A later wording change is a new version file `S<n>.v2.yaml` with `amends`, `reason`, `date` and voids earlier verdicts (FR-004).
2. **A shakedown may change the structure of a model, never the predicted outcomes already derived from it.** Expected values come from the documented behaviour of the tools, never from the shakedown result. Before the freeze a shakedown may change the structure of a model the criteria use (the block-allocation model of S2, the cells and rows of the S4 state table); a predicted outcome that has already been derived is not edited to match an observation, and a later mismatch is a FAIL, not a re-prediction (spec verdict model, rule "Run"; plan O2).
3. **Graphify-first authoring** (constitution): before any task that authors a new named function, module or CLI command (everything under `spikes/phase0/` that defines named functions or modules: `testlib/`, `spikectl/`, `guest/`, `controls/`, `vm-tests/` including `checks_*.py` and the test scripts, `nix/` modules and helpers such as `mkspike.nix`, and the helpers in `tests/`), run `graphify query "<intent>" --budget 1500` (plus `graphify path` or `graphify explain` where a specific relationship matters), evaluate every returned candidate and state the candidates evaluated in the commit body. The current graph is docs-only, so the expected outcome is "no candidate". Do not refresh the graph on this feature branch (linked worktree). If a graphify call fails, warn, continue and flag it for review.
4. **No product code** (SC-010, constitution phasing discipline): no backend, API, UI, Docker or VM management task exists in this file. The reference mover, lock daemon and apply script are scaffolding and say so in their file headers.
5. **Constitution hygiene**: Conventional Commits (`build(phase0)`, `test(phase0)`, `docs(phase0)`, ...); all work lands on `main` through PRs, merged by rebase (preferred, for a linear history) or merge commit, never squash; a merge commit MUST replace GitHub's auto-generated "Merge pull request ..." subject with a Conventional-Commits header before merging (constitution, merge-strategy-no-squash). Recorded deviation: the merge commits of PRs #1, #4, #6, #7, #9 to #12 and #14 to #16 and the merge `9feb1d7` carry auto-generated subjects (PR #13 was rebase-merged); history is not rewritten, the rule applies from now on; no absolute host paths, user names, host names or secrets in any committed file (guest paths such as `/mnt/archive/...` are fine); files over 500 lines are split or carry a documented reason; test code lives in separate files from harness code (`spikes/phase0/tests/`, `spikes/phase0/vm-tests/`); before every handoff the PR description reports which checks were run (formatter, static checks, `nix flake check`, unit tests) and which were unavailable or skipped.
6. **Frozen contracts**: `contracts/*` and the other approved documents are read-only inputs. If a task discovers that a contract must change, it opens a separate reviewed docs PR (see Open items); it never edits the contract inside a harness PR.
7. Tasks labelled **GATE** are human steps (review, merge, runner decision) that cannot be done by an agent; later tasks depend on them.

## Implementation Strategy

### MVP first (S1, then S2)

1. Complete Phase 1 (Setup) and Phase 2 (Foundational); the Foundation checkpoint proves the verdict model and the fault kinds before any spike relies on them.
2. Complete Phase 3 (S1) through `T056`: the cheapest spike, the one that can end the tiered design earliest. A FAIL is a valid result and triggers the ADR-0002 fallback decision.
3. In parallel or directly after, complete Phase 4 (S2) through `T080`: the recovery claims and the gating that ADR-0002 rests on.
4. **STOP and VALIDATE**: with S1 and S2 recorded, the storage model's two largest risks are decided; review whether to continue before investing in S3.

### Incremental delivery

1. S3 (the mover), then S4 (lockouts); each ends with its own record PR and checkpoint.
2. S5 whenever a person is free (probe first); it is independent.
3. Phase 8: reproducibility, CI, verdict matrix, the separate ADR PR.
4. Phase 9 (X1) only on request; Phase 10 (X2) only on request and after the S1 to S4 checkpoints; Phase 11 last.

### Delivery through PRs

One PR per criteria freeze and one per record keeps "criteria before results" visible in history. Harness PRs may be batched per phase. Merge by rebase (preferred) or by a merge commit whose subject is a Conventional-Commits header (rule 5), never squash. Criteria PRs of S1 and S2 may be batched if the lock lines of both are merged before either record-mode run.
