- In Go tests, prefer small hand-written fakes over generated mocks, use `net/http/httptest` for HTTP, and hide external-program runners behind a small replaceable interface so tests do not execute real system commands. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In Go tests, run `go test ./...` for the complete module as appropriate, with `-race` for concurrent code, `-count=1` when a result may depend on external state, and following project-specific tags, build constraints, and test-runner requirements. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In Go tests, run the race detector for code that uses goroutines, channels, or shared state and treat a reported race as a defect, add a fuzz test for parsers and decoders that process untrusted input, and add benchmarks only for code whose performance has been measured to matter. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In Go tests, test behavior and contracts, including important failure paths, rather than mirroring private implementation details. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In Go tests, use table-driven tests with `t.Run` subtests when several inputs share one behavior, with descriptive case names and clear expected results. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In Go tests, use the helpers of the `testing` package (`t.Helper()`, `t.Cleanup`, `t.TempDir()`, `t.Setenv`) and call `t.Parallel()` only for tests that share no state. _[from `com.github.haexmas.atoms.coding-guideline-go/go-testing`]_
- In JavaScript and TypeScript code, follow the existing runtime and module-system conventions and do not assume that a platform-specific global or API exists in every environment. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, keep modules and exports focused, prefer named exports for reusable library code, and avoid circular dependencies. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, prefer `const` and narrow local mutation, and prefer immutable transformations at shared boundaries while allowing simple local mutation when it is clearer. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, preserve error causes when translating errors and add useful context at a boundary. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, treat TypeScript `strict` mode as the baseline for new or actively maintained code, and use a precise type, a generic, or `unknown` with explicit narrowing instead of `any`. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, use `===`/`!==`, `??`, and `?.` deliberately, and decide how absence of a required value is handled. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, use the project's configured formatter, linter, compiler, and test runner, and TypeScript changes SHOULD pass `tsc --noEmit` (or the project's equivalent), linting, formatting checks, and the relevant tests. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript tests, choose the narrowest test level that proves the behavior: unit tests for pure logic, integration tests for module boundaries and persistence, and end-to-end tests for critical user journeys. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, keep mocks narrow and behavior-oriented, mocking an external boundary only when isolation or determinism requires it. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, keep tests deterministic and isolated, controlling time, randomness, environment, and external clients at explicit boundaries and avoiding real network calls, shared mutable state, uncontrolled random values, and arbitrary timer sleeps. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, keep type-level tests separate from runtime tests when the project needs to verify inference, assignability, or declaration output. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, prefer a small number of clear assertions per scenario, with test names describing the behavior and relevant condition. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, test both successful and failure behavior, including malformed input, missing values, rejected promises, cancellation or timeout behavior, and authorization or persistence failures where they matter. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, test observable behavior and public contracts rather than the arrangement of private functions or implementation details. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- In JavaScript and TypeScript tests, use the repository's configured runner, environment, formatter, linter, and compiler, include relevant tests with a change, and confirm that the runner configuration discovers the test file. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Explain in comments why a non-obvious decision exists, what invariant must be preserved, or which external constraint applies, and update comments when behavior changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Follow a repository's already documented structure, naming scheme, or size convention unless the task explicitly changes it; these defaults are not a reason to reformat or reorganize an entire codebase. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Give a file one primary reason to change, and split it when it has unrelated responsibilities, independent public concepts, different change owners, or tests that are difficult to isolate. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Give each function one coherent responsibility at one level of abstraction, extracting a helper when it names a concept, makes a branch independently testable, or removes repeated logic. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep dependencies directed and understandable, and put I/O, framework adapters, and process wiring at the edges when the architecture calls for such a separation. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep each change self-contained and easy to review, with production code, relevant tests, documentation, and configuration together when they describe the same behavior, and split independent refactors and unrelated cleanups into separate changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep public module interfaces narrow and intentional, hiding implementation details behind the smallest stable API the callers need. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep related tests, documentation, fixtures, and call sites close to the behavior they verify and updated after a module split, according to language and repository convention. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep side effects at visible boundaries so that pure calculations and decisions are easy to test without a database, network, filesystem, clock, or global mutable state. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Name code after its domain meaning and behavior, preferring a clear name over a comment that explains an opaque `data`, `helper`, or `process` function. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Organize code around cohesive domain or feature boundaries where the codebase supports it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer a change that clearly improves maintainability and correctness over theoretical perfection, and when a design is uncertain make the smallest reversible change that provides evidence about the next decision. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer early returns or named helpers when they make the main path easier to follow, reducing nesting. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Refactor repeated behavior when the shared rule is real and the abstraction makes both callers clearer, keeping the abstraction close to the domain that owns it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Review deliberately a function or method beyond roughly 40–60 lines or nesting deeper than roughly three levels, treating these thresholds as heuristics rather than targets or mandatory limits. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Separate broad formatting or mechanical refactors from behavior changes when possible. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Test observable behavior so that a test can fail for a real regression. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat a change of about 100 net lines as a review-size warning, and split the work or agree on the larger change in advance when it approaches 1000 lines. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- For any question about the codebase (what something does, where it lives, how pieces relate, which existing artifact might already satisfy a request, or how to trace a symptom to its source), run the graphify context-map operation first, before a raw `grep`/`rg` search or broad file reads, including exploratory lookups incidental to a larger task; the only exemption is a local one-file edit at a symbol whose location is already known from earlier in the same task. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Perform the context-map operation by stating the concrete intent as a question, choosing a small token budget (start around 800–1500 tokens and increase only when the relationships are insufficient), running `graphify query "<intent>" --budget <N>` (with `--dfs` for a narrow dependency path, and `graphify path` or `graphify explain` for one specific relationship or symbol), treating the result as a map and reading only the smallest source slices needed, and, if the result is truncated or ambiguous, narrowing the question or making one additional focused query. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Preserve in the resulting context map, when available, the task intent and token budget, selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit truncation or failed-consultation note. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_
- Extract and propose a refactor for six or more identical lines with the same logic across candidates; leave fewer than five purely structural lines (setup, error-wrapping, adapter boilerplate) alone, and leave hits inside test files alone unless they are helper functions. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Leave duplicated arrange/assert/setup blocks across test cases alone, since each test's setup documents its assumptions in place. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Mark deliberate simplifications that cut a real corner with a known ceiling (global lock, O(n²) scan, naive heuristic) with a `ponytail:` comment naming the ceiling and upgrade path. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Pick the edge-case-correct option when two stdlib approaches are the same size. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Prefer deletion over addition, boring over clever, and the fewest files possible; the shortest working diff wins, but only once the problem is understood. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_
- Question complex requests ("Do you actually need X, or does Y cover it?"). _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## SHOULD_NOT

- In Go code, avoid catch-all package names such as `util` or `common` and stutter such as `user.UserService`. _[from `com.github.haexmas.atoms.coding-guideline-go/go`]_
- In Go code, avoid `init()` functions and mutable package-level state. _[from `com.github.haexmas.atoms.coding-guideline-go/go`]_
- In JavaScript and TypeScript code, avoid `any` and keep untyped escape hatches local and explained. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, do not catch an error merely to log and rethrow it unchanged. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, do not introduce a barrel export or a new abstraction only to shorten an import path. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, do not replace repository tooling with a personal global installation. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript code, do not use mutation or shared mutable module state as an accidental communication channel. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- In JavaScript and TypeScript tests, do not mock the unit's own logic so thoroughly that the test only verifies the mock wiring. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Abstract two things merely because they look similar without first establishing that they share behavior, ownership, change reason, and invariants; a small amount of local duplication is preferable to a premature generic abstraction. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Add artificial wrappers, blank lines, or extra files, or pad files up to 500 lines, only to satisfy a line-count threshold. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Create folders only for superficial symmetry, such as putting every small class, interface, or helper in its own folder. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Enforce a universal maximum for functions, files, or pull requests, since domain complexity, cohesion, control flow, and the number of reasons to change matter more than line count. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Introduce circular imports, hidden global state, or a domain layer that knows about infrastructure details. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Narrate in comments code that could be made clear through structure and naming. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Re-export everything or create pass-through modules that add no boundary, and avoid a generic utility module becoming a dumping ground. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Scatter one simple operation across many microscopic functions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Split a file solely to make it shorter. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not add a new dependency if it can be avoided. _[from `com.github.haexmas.atoms.ponytail/ponytail`]_

## MAY

- Exceed the review-size thresholds for generated code, mechanical renames, and required migrations, provided they are identified as such. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep a language-required test-module declaration or registration in the production file. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
